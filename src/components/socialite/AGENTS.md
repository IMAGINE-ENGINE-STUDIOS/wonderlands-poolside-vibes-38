# SOCIALITE rules
- SOCIALITE state (`pf_*` localStorage keys, except `*_token`) syncs to `socialite_state` via SocialiteCloudSync, per owner_id (main admins share the all-zero owner) — why: posts/settings follow each user across computers.
- Timed SOCIALITE sends (posts/email/SMS/WhatsApp/calls/contact sends; list shown inside Calendar, time zone chosen per send) go in `socialite_scheduled` and are sent by the `socialite-scheduler` edge function (pg_cron every 5 min); all platform posting lives in `supabase/functions/_shared/socialitePublish.ts` — why: sends must fire with the browser closed, and one publisher avoids drift.
- `/socialite` uses its own sign-in (SocialiteGate) on the shared Wonderlands auth; company sections are main_admin only — why: one account across both sites without exposing company data.
- All SOCIALITE client sends (email/SMS/WhatsApp/quote/invoice/promotion/referral) go through `src/lib/socialite/clientActions.ts` and log to communication_logs — why: one send path keeps history and behavior consistent. SOCIALITE "Admin" is a focused growth hub (performance, promotions, quotes/invoices, referrals, sequences), not the full /admin.
- SOCIALITE social keys are per user (socialite_credentials.owner_id); publishing uses the poster's own keys. Non-admin users message only their own uploaded contacts (socialite_contacts) via the socialite-send edge function — why: every user brings their own accounts and audience without touching company clients.
- Dashboard & Analytics merged in SocialiteInsights; live platform metrics via socialite-insights edge function (per-user keys) — why: one real-data screen.
- SOCIALITE commercial layer: plans/config in `socialite_plans` + `socialite_billing_config` (admin-edited via RLS); Stripe checkout/verify/cancel in `socialite-billing` (no webhook — verify on return, status re-reads Stripe hourly); every post/send/Genius call is metered by `_shared/socialiteBilling.ts#meter` (dry-run before, record after) — why: one place enforces plan limits, credits and overage.
- SOCIALITE Genius = admin-supplied AI provider key (any OpenAI-compatible, Anthropic or Gemini), encrypted in `socialite_ai_config` and only used by `socialite-ai`; public UI says "Genius", never "AI" — why: admin brings their own provider and customers pay per the admin's AI revenue model.
- SOCIALITE public API = `socialite-api` edge function (v1, Bearer `sk_live_` keys stored as SHA-256 in `socialite_api_keys`, scopes, 60/min via `socialite_api_requests`); keys managed by `socialite-api-keys`; SDK is `public/sdk/socialite.js` — why: owner-scoped only, never exposes company data.
